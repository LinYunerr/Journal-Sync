# i18n 决策待定项

2026-09-07 中英文转换改造自检中确认的两个开放问题。两者都涉及产品取向，未做任何代码改动；在用户明确决策前不得实现。

## 1. 英文用户的数据默认值是中文

**现象**：`DEFAULT_SETTINGS` 中的数据默认值是中文字面量：

- `diaryPath: '日记'`（日记存放文件夹，`src/main.js`）
- `filenameRule: 'YYYY-MM-DD 日记'`（日记文件名规则，`src/main.js`，回退值同样出现在 `src/core/diary.js` 与设置页空值兜底）

英文用户首次使用时，插件会创建 `日记/2026-09-07 日记.md`。这不是翻译遗漏——这些值是**持久化数据**而非 UI 文案，刻意不包 `t()`。

**为什么不能简单翻译**：路径/文件名规则一旦生成就会写进用户的 vault 结构和已有链接。如果默认值跟随界面语言，用户切换语言后新建文件会落到不同文件夹、不同命名，造成库内不一致。此外 `deepMergeSettings` 的语义是「非空用户值优先」，默认值只在用户未填写时生效，翻译后新旧用户的默认路径会不同。

**待决策方向（举例，非结论）**：

- A. 维持现状：默认值固定为中文，英文用户可自行修改设置（成本最低，现状即如此）。
- B. 首次初始化时按当时语言生成默认值，之后永不跟随语言变化（需要区分「用户显式设置」与「初始默认」，改动 settings 合并逻辑）。
- C. 默认值改为语言中立（如 `YYYY-MM-DD Journal` / 文件夹 `Journal`），对中文用户是破坏性变更，需迁移。

## 2. `@图片N` 图片 token 对英文用户显示为中文

**现象**：`@图片N` 是跨模块的内部数据协议——`main.js` 生成、`payload.js` / `telegram-markdown.js` / `send-log.js` 用正则 `/@图片\d+/` 匹配，并持久化在预设与发送日志快照里。因此它刻意不参与翻译，中英文界面都显示 `@图片1`。

对英文用户的影响：

- 编辑器中的图片占位 chip 显示 `📷 @图片1`；
- 触发图片提及下拉需要输入 `@图`（`send-modal.js` 的触发正则只认中文「图/图片」前缀）。

**为什么不能直接翻译**：token 会随内容一起保存、随快照恢复。若 token 文案跟随语言，切换语言后旧笔记/旧快照里的 token 将无法被正则匹配，图片关联全部断裂。

**待决策方向（举例，非结论）**：

- A. 维持现状：token 固定中文，仅接受英文用户输入门槛（成本最低）。
- B. 双协议支持：正则同时接受 `@图片N` 与 `@img N`（或 `@image N`），显示层跟随语言，持久层保留原 token。属于新功能，需明确立项。
- C. 仅放宽触发：提及下拉的触发正则额外接受 `@i` / `@img` 前缀，token 本身不变。属于新功能，需明确立项。
